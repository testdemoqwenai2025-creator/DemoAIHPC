Lazy Evaluation as a UX Primitive

Popups open immediately with a "pending" state and stream updates as the computation progresses. Users feel progress rather than blocking — the "feels alive" property that's hard to copy.

What it is

A lazy-evaluated popup is a UI container that appears instantly (zero perceived latency), shows a streaming progress trace, and progressively fills in the result as sub-steps complete. The viewer sees the computation happening rather than waiting for it. This is in contrast to a blocking spinner that hides the work.

Where the idea came from

Streaming UIs became mainstream with chat-GPT-style token streaming (OpenAI, 2022), but the pattern is older: server-sent events in modern web standards, Observable notebooks' reactive cell updates, and Unix pipes' progressive output. The "popup" framing is what makes it a reusable UX primitive rather than a one-off.

Why it matters for AIHPC

  • Perceived latency. A 5-second computation feels instant if the popup opens in 50ms and streams updates every 200ms.
  • Trust. When the viewer sees steps arriving, they trust the result more than a black-box spinner.
  • Composability. Each step can be a sub-trace (see Replayable Decision Traces); the popup becomes a viewer onto the trace.
  • Pedagogy. A student can pause mid-stream to inspect an intermediate value.
  • Cancellation. Long-running computations get a Cancel button because the popup owns the lifecycle.

How AIHPC Advanced implements it

  • Today. The OLS demo's execution-trace popup streams steps (parse → XᵀX → invert → Xᵀy → β̂ → RSS → plot) with progress dots. Each step has a 180–280 ms cadence so a viewer can read it.
  • Server-side (later). SSE or WebSocket from a sandboxed runtime pushes trace events as they happen. The popup renders them in real time.
  • Cancellation. The popup's close button aborts the underlying computation (AbortController for fetch; worker terminate for in-browser).

Evolution of the subject

  • Today. Pure client-side streaming with setTimeout cadence.
  • Phase 4+. SSE stream from a sandboxed runtime; each trace event is a JSON object on the wire.
  • Phase 5+. Popups compose — open a sub-popup from any step to inspect the sub-trace.
  • Phase 6+. "Thinking" tokens become inspectable — click any token to see its grounding in the knowledge graph.

Open questions we want to be wrong about

  • Is SSE enough or do we need WebTransport for sub-50ms latency traces?
  • How much should a viewer be able to intervene mid-stream (pause, edit input, branch)?
