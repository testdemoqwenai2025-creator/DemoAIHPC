Provenance-First Computing

Every result is a first-class artifact with full provenance: input data, math, code, execution trace, output, report. Reproducibility isn't a feature; it's the substrate. The "surpass AETHEL" thesis rests here.

What it is

A provenance receipt is a JSON document that travels with every downloadable result. It records: the demo manifest (math, code, annotations), the input data hash, the runtime (browser / server-sandboxed), the version of every library touched, the execution trace, the output hash, and the timestamp. Given the same manifest, same input, and same runtime, the result is bit-for-bit reproducible.

Where the idea came from

Provenance research is old — W3C PROV (2013), OPM (2008), the Open Provenance Model. Notebook platforms (Jupyter, Observable, Pluto) ship partial provenance (code + outputs). Scientific reproducibility crises across fields (psychology, oncology, ML benchmarking) made it topical. AIHPC Advanced's contribution is to make provenance first-class — not optional, not enterprise-tier, but the default substrate of every artifact.

Why it matters for AIHPC

  • Audit without NDA. A reviewer can verify a claim by replaying the trace locally; they never need to access your private data.
  • Citation. A demo result cites its own provenance receipt; a paper cites the demo URL. Citations become computable.
  • Composability. Workflow A's output is workflow B's input; the receipts chain. The composite receipt is itself a receipt.
  • Versioning. AETHEL's knowledge graph updates an edge; the old edge isn't deleted, it's superseded with a pointer. History is recoverable.

How AIHPC Advanced implements it

  • Manifest. The DemoManifest TypeScript schema (see src/lib/demos/manifest.ts) declares the math, code, annotations, datasets, observability, and runtime for each demo.
  • Receipt. A ProvenanceReceipt JSON file is generated alongside every downloadable CSV / JSON. It includes manifest hash, input hash, output hash, runtime info, and a link to the trace.
  • Trace. See Replayable Decision Traces. The trace is part of the receipt.
  • Receipt URL. The receipt is content-addressed (SHA-256 of its content) so the same URL always returns the same receipt — no version drift.

Hypothetical demo

Ship a provenance receipt alongside every downloadable CSV

Imagine: you run the OLS demo. You click "Download CSV" and you get two files — the data and a receipt. The receipt is what makes the CSV citable. Below is a sketch of what the receipt would look like. 

{
  "@context": "https://aihpc.advanced/prov/v1",
  "manifestHash": "sha256:7fe6475...",
  "manifest": {
    "id": "linear-regression",
    "version": "v0.2.1",
    "runtime": "browser",
    "dataResidency": "downloadable"
  },
  "input": {
    "dataHash": "sha256:8a3f1b...",
    "n": 6,
    "source": "user-edited in-browser"
  },
  "output": {
    "csvHash": "sha256:c2d9e0...",
    "beta": [0.066667, 1.971429],
    "rss": 0.042857,
    "r2": 0.999524
  },
  "trace": {
    "url": "trace://ols/7fe6475.../trace.json",
    "steps": 7,
    "format": "json-ld"
  },
  "environment": {
    "client": "browser",
    "timestamp": "2026-10-19T10:14:52Z"
  },
  "signature": "sha256:...",
  // Re-run: same manifest + same input + same runtime
  //  => same output hash. Bit-for-bit reproducible.
}

Evolution of the subject

  • Today. Manifest exists; receipt is sketched on this page; CSV download is real but no receipt yet.
  • Phase 4+. Receipt auto-generated alongside every CSV download; receipt content-addressed.
  • Phase 5+. Receipt cross-references AETHEL knowledge graph — every output edge gets a provenance receipt.
  • Phase 6+. Receipt becomes citable — a DOI-style identifier minted from the receipt hash. Citations become computable.

Open questions we want to be wrong about

  • Should the receipt live alongside the CSV (two files) or be embedded (one file with metadata)?
  • Where do receipts get content-addressed when there's no server? Client-side SHA + IPFS-style pinning later?
  • What's the right schema — W3C PROV-O, JSON-LD with a custom @context, or both?
