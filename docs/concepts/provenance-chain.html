Provenance Chain

Every result has a graph of evidence — the directed acyclic graph (DAG) of steps that assembled it. The Provenance Chain visualisation renders this DAG as a layered flow: each node is a step (input, parse, compute, annotate, output), each edge is a typed data dependency. A node may have multiple inputs (a join) or multiple downstream consumers (a fork). Press play to watch the DAG assemble itself in topological order.

What it is

A provenance chain is a directed acyclic graph (DAG) that records how a result was assembled. Unlike the{' '} replayable decision trace (which captures the agent's evolving state), the DAG captures the data flow: this dataset and that database fed this parser which forked into three analyses which rejoined at this annotation which converged with this visualization at the final receipt. A node may have multiple inputs (a join) — meaning its computation only fires once all upstream data has arrived. A node may have multiple outputs (a fork) — meaning its result feeds several downstream consumers. Every edge is a typed data dependency; every node has a content-addressed hash.

Where the idea came from

The user described the vision as bedrums or footpaths or chains how successive scenario was evolve or put together. The natural mathematical structure for this is a DAG — the same structure used by W3C PROV-O, the Open Provenance Model (OPM), Airflow / Prefect / Dagster pipelines, Makefile dependency graphs, and Git's commit DAG. The layered layout shown above assigns each node to a layer (its longest distance from any source), then places layers left-to-right. Topological traversal — the order in which nodes appear during "Walk the DAG" — guarantees that every node's inputs have already been computed.

Why it matters for AIHPC

  • Trust. The viewer can see exactly which steps produced the result they downloaded. No black box.
  • Audit. The DAG is itself a downloadable artifact; a reviewer can replay it offline.
  • Citation. A paper citing a result cites the DAG URL — a content-addressed provenance receipt.
  • Composability. The DAG of demo A can become one input to demo B's DAG; the DAGs merge cleanly.
  • Failure isolation. When a result is wrong, the DAG tells you exactly which node introduced the error — and which downstream nodes are tainted by it.
  • Parallelism. Nodes in the same layer have no data dependency between them — they can run in parallel. The DAG is the natural unit of work-stealing schedulers.

How AIHPC implements it

  • Node format. { id, kind: 'input'|'parse'|'compute'|'annotate'|'output', label, dataHash, createdAt, layer }
  • Edge format. { from, to, kind: 'data'|'metadata', typedAs } — many edges can target one node (join) or leave one node (fork).
  • Layer assignment. Longest-path-from-source: layer(node) = max(layer(input) + 1) for each input, or 0 for sources. O(V+E).
  • Topological order. Kahn's algorithm (BFS over in-degree zeroing) — the order in which "Walk the DAG" reveals nodes.
  • Visual. SVG with nodes positioned in columns by layer; curves between layers. Animated flow dots traverse each edge in topological order.
  • Receipt. The whole DAG is serialised as JSON-LD with the prov: namespace; each node lists its inputs: [] array; downloaded as a Blob alongside the result.

Evolution of the subject

  • Today. The DAG visualisation above is a sketch with a hypothetical 10-node nucleotide-analysis DAG — 2 inputs, 4 compute, 2 joins, 1 receipt.
  • Phase 7+. Every demo runner emits its DAG alongside the CSV / FASTA / receipt download.
  • Phase 8+. DAGs compose — a workflow that runs three demos in sequence produces a DAG that references each sub-DAG by ID; merges are first-class.
  • Phase 9+. DAGs are content-addressed and shareable by URL — a citation becomes a one-click replay.
  • Phase 10+. Same-layer nodes are scheduled in parallel by a work-stealing runtime; the DAG becomes the unit of distributed compute.
